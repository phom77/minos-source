# Solve workspace — 2026-10-08

The owner requested a LeetCode-style code/submission screen. This supersedes the earlier centered reader/editor composition in `submission-flow.md`, while retaining Minos identity, the approved compact application header and existing backend capabilities.

Reference evidence: the [current problem page](https://leetcode.com/problems/two-sum/description/) identifies Description, Code, Testcase and Test Result regions; the official [coding guide](https://support.leetcode.com/hc/en-us/articles/360012016874-Start-your-Coding-Practice) documents the split reader/editor, editor controls and submission feedback. Its screenshots are an older composition, not a claim of exact current styling. The live reference could not render in the local browser because DNS resolution failed. The approved Minos brand board and Settings references remain the visual source for palette, typography, borders and application navigation.

## Screen contract

- Purpose: read the statement, compose C++20, submit and understand the result without leaving the editing workspace. Submit is the primary action.
- Desktop: fill the available width and height below the application header. Description and code use separate panes with their own scrolling. Put the problem title and limits inside Description, rather than a large heading above the workspace. Keep the editor toolbar, language and submit action visible; show a lower console for public examples and actual submission results.
- Smaller screens: stack description and editing areas with a direct Code jump; preserve both sections and source rather than destroying the editor on a breakpoint change. At narrow/short viewports, let the document scroll instead of trapping content inside an undersized fixed viewport.
- Editor: numbered lines, a cursor-position readout and a working expand/restore control. Keep the native textarea's selection, undo, IME and Tab-to-exit behavior. No synthetic syntax parser, fake settings or nonfunctional toolbar controls.
- Console: accessible Examples/Result tabs with arrow/Home/End navigation. Examples show only public sample data. After admission, select Result and follow the actual owner submission with the existing serial polling policy. Preserve editable source for another submission and provide a link to the durable owner detail.
- States: guest/sign-in, quiet validation, duplicate-click suppression, admission overload, ambiguous POST, queued/judging, all verdicts, legacy/infrastructure failure, interrupted reads and expired/private results. Private evidence and source must clear on identity changes.
- Keep constraints, CSRF, source bounds, version pinning, memory-only drafts and ambiguous-POST handling intact. Custom Run, hidden test contents, fabricated performance comparisons, discussions and editorial tabs remain outside the existing capability boundary.

## Implementation and verification

`ProblemDetailPage` owns the split/expanded layout and mobile Code jump. `SubmissionForm` retains admission, draft and session responsibilities and tracks the admitted owner result in its console. `CodeEditor` owns native text editing presentation, cursor position and a virtual line gutter; a 1,000-line file renders only the visible line numbers. `SubmissionResultView` shares actual verdict/evidence presentation between the inline console and durable detail. No backend change or new production dependency is required for this layout.

After admission, source remains editable in the same workspace. The admitted text is acknowledged for the reload warning; editing it again restores the unsaved-work warning and account-memory draft. Inline reads stop on terminal state, navigation, identity change or failure. An interrupted read preserves the last result; permission failures clear private evidence. API additions such as the optional test summary are tolerated by the existing validated projection; every test row remains visible in the result's scroll region.
