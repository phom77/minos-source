## Screen contract

| Screen | Purpose and primary action | Essential information | Interaction states |
| --- | --- | --- | --- |
| Latest problem reader | Read, write C++20 and submit | Statement, whitespace-preserving samples, current version, limits, source and byte count | Public loading/missing/retry; guest composition and sign-in; quiet validation, linked error summary, pending, rejected or unconfirmed submission |
| Submission detail | Understand the outcome; edit and submit again | Pinned public title/version, submission time, actual verdict, maximum test measurements, compiler diagnostics, ordered test outcomes and submitted source | Queued, judging, all seven verdicts, legacy completion, system failure, interrupted updates, missing/private/expired session, copy feedback |
| Submission history | Find and open an earlier submission | Public problem title/version, result, submission time, page size and pagination | Loading, empty, invalid/beyond-last page, outage/retry, active updates, permission/session changes |
| Historical problem reader | Inspect the statement used for a submission | Exact public version and samples; explicit action to solve the latest version | Immutable reader without a historical-version submission form |

Desktop places the statement and editor together. Mobile stacks them and provides a Write code jump. The editor is a native labeled textarea with no keyboard trap. History uses a table on larger screens and compact linked rows below 768px, so its title and result stay visible. Test evidence and long source/diagnostics scroll inside their own regions. Navigation, heading hierarchy, focus outlines, status labels and error announcements work without color alone.

No slogans, decorative explanations, account IDs, submission UUIDs, attempt IDs or toolchain digests appear in ordinary UI. The exact-output consequence remains because whitespace and line endings affect the result. Infrastructure failure and older results without a verdict have concise explanations to prevent confusing them with a contestant failure or Accepted.

## Behavior and boundaries

- `SubmissionsApi` sends only `language: cpp20` and bounded raw source to the current problem endpoint. Existing same-origin session and CSRF interceptors protect the request. Returned problem/version identity is authoritative; the browser cannot select a historical version for admission.
- Source validation checks nonblank text, null characters and the 65,536-byte UTF-8 limit. Unchanged blur is quiet; edit/blur reveals errors; correction updates a revealed error; submit validates and focuses a linked summary. Invalidity never disables Submit. Pointer submission does not move its target when blur feedback appears.
- A pending request prevents duplicate clicks. An outstanding POST survives view teardown, but a stale identity cannot navigate to its result. There is no automatic POST retry. A timeout, server error or malformed success response preserves source and directs the user to history before another submission. Overload uses a safe Retry-After hint.
- One bounded draft remains in memory for the active account across internal navigation. It never enters browser storage and is cleared when identity changes or submission succeeds. A full page reload with unsent code triggers the browser's unsaved-work warning. Guest source survives signing in on the same screen. Drafts are not durable across reloads, browser restarts or editing multiple problems.
- Detail and history perform serial reads about every 2.5 seconds while submissions are active. Hidden tabs pause repeat reads; terminal states, errors, navigation and identity changes stop them. Poll failures preserve the last useful result and offer Refresh. Permission/session failures remove private evidence.
- Result UI uses the recorded verdict and per-test evidence. Unexecuted tests say Not run and missing measurements remain a dash; zero stays zero. Maximum CPU/wall/memory values describe executed tests, excluding compilation. Compiler diagnostics and source are escaped plaintext. No hidden test inputs, expected answers or runtime stdout/stderr are displayed.
- Edit & submit again restores source and focuses the latest problem's editor. It creates an ordinary new submission; it is not manual rejudge. Custom execution/Run, contests, ratings and new languages remain deferred.
- History only fetches source-free summaries. The existing summary contract lacks a problem title/version number, so public version lookups supply those labels, deduplicated per page with four concurrent reads and a bounded cache. A missing/archived public version uses an unavailable label while the owner's recorded result remains accessible. A future enriched history projection could eliminate these lookups; it is not required for this frontend slice.
