# Judging completeness and performance plan

Date: 2026-10-07
Owner authorization: implement the phased judging improvements discussed on this date.

The owner requires every private test to be judged after successful compilation, including tests after a contestant failure, and an accurate passed-test count. This changes the M6 first-failure policy. M8 custom execution, public deployment and distributed workers remain outside this plan.

## Phase 1 — Complete test results and counts

Status: implemented; Domain, real PostgreSQL/HTTP and native sandbox count regressions passed. The standalone foundation script remains syntax-checked only.

- Compile once per attempt; run every pinned private test unless infrastructure fails or the attempt is cancelled.
- Accepted requires every test to pass. Otherwise use the failure of the earliest failed test in published order, independent of later failures or eventual execution order. Existing per-test resource-limit precedence remains unchanged.
- Expose total, executed, passed and failed test counts in the owner's result. CompilationError has zero executed/passed/failed tests. Pending, Judging and SystemFailed have no final result summary. Pre-M6 markers have no invented counts; historical M6 results retain NotExecuted tests and accurate executed counts.
- Preserve exact checking, authorization, pinning, leases, retries, cleanup and historical evidence. No migration or rewrite of existing results.
- Update Domain, executor, HTTP/PostgreSQL tests and the executable foundation rehearsal.

Exit: mixed failures and later passes survive completion/restart with correct counts; incomplete or stale evidence cannot finalize; build, relevant Windows tests and disposable Linux/PostgreSQL/HTTP checks pass.

## Phase 2 — Reduce execution overhead and measure it

Status: implemented and fixture-validated on 2026-10-08. Docker's paired compile-plus-100-test timing improved from 146.565 to 105.902 seconds (27.74%). The owner requested further optimization; the real opt-in Isolate adapter now completed HTTP/PostgreSQL judging in 2.096 seconds (100/100 Accepted) and 2.025 seconds (67/100 WrongAnswer), including all tests/checks and immediate claim, excluding startup/queue polling wait. Its output gaps from the earlier Python prototype are fixed. The full native suite passed 20 Domain and 172 integration tests; only Windows ACL was skipped. Docker remains the default. Live native hosting requires validated host policy; this WSL's piped core collector is deliberately rejected. See [evidence/reproduction](judging-performance.md) and [ADR 0013](adr/0013-native-per-test-runtime.md).

Baseline: 88.833 seconds for one compilation and 100 serial executions of a trusted C++20 sum fixture, excluding API/database/queue time. Run stages spend 78.558 seconds outside the runtime stopwatch. Evidence: ignored `artifacts/judge-timing-20261007/result.json`.

- Measure compile, artifact verification/read, provisioning, execution, evidence and cleanup durations without source, hidden contents or high-cardinality labels.
- Benchmark a lightweight native Linux sandbox candidate, such as Isolate, against Docker. Preserve the pinned compiler, per-test isolation, descendant accounting, limits and cleanup. Evaluate native/Compose deployment implications before selecting a default; do not weaken the existing Compose boundary for speed.
- Remove redundant movement/control-plane work with verified immutable snapshots and bounded disk/memory use. Do not preload all tests into unbounded memory or expose expected answers to submitted code.
- Repeat the same 100-test fixture and include CPU-heavy, output-heavy and failure cases. Separate cold startup, warm execution and queue latency. A 2–3 second target applies only to an explicitly measured lightweight workload.
- Native slice implemented: independently bounded stdout/stderr including ignored signals; complete evidence through the existing port/policy; compilation failures, overlapping limits, cancellation, missing metadata, hostile scratch and attempt/retry semantics validated. Preserve one fresh sandbox/process per test; batching checks measured negligible savings. The approved experiment does not change the default runner.

Exit: candidate passes existing adversarial/cleanup/verdict fixtures and has reproducible before/after timing. Record adapter selection and deployment requirements before changing the supported default.

## Phase 3 — Bounded concurrency and replaceable job delivery

Status: implemented on 2026-10-08. One Worker defaults to two active submissions, with a retained processing scope and independent renewals per job. A shared FIFO budget bounds compile/runtime slots and requested memory plus scratch, validates management CPU/RAM reserve before claims, and blocks new execution/delivery after cleanup uncertainty. PostgreSQL ID delivery is separated from targeted durable claiming and processing. Tests within a submission remain sequential; the current single native box still serializes runtimes while allowing Docker compilation overlap. See [ADR 0014](adr/0014-bounded-worker-scheduling.md) and [operating configuration](operations/development-runbook.md#operational-alerts).

- One long-lived Worker manages a validated bounded execution budget on one Linux machine, with a scope per job and independent renewal. Reserve CPU/RAM for compilation and management.
- Schedule submissions and, where beneficial, tests within one submission under the same machine-wide budget. Results retain published order; cancellation waits for all cleanup.
- Separate obtaining a job ID from claiming its durable attempt and processing the submission. PostgreSQL polling remains implemented; a future MQ consumer calls the same use case by job ID without raw source/private tests in messages.
- Keep database authority for attempts/results and idempotent completion. A future broker requires atomic submission-to-delivery handoff, confirmations, duplicate handling, durable retries and expired-lease recovery; add an outbox only with that concrete requirement.
- Load-test queue/completion P95, fairness, cancellation, overload and recovery. Multiple machines/public capacity need a separate measured hosting decision.

Exit: concurrency stays within budget; mixed jobs complete with correct counts, no stale completion or cross-job access; delivery is replaceable and tested without an unused broker.

- Phase 3: implemented and validated. No new production project, layer, package or broker. Resource reservations never exceeded two slots/the 1152-MiB test budget. Windows final release build had zero warnings/errors and 13 targeted scheduler/budget/architecture tests passed. ## Follow-up: compile allocation and multiple Isolate boxes

Owner-authorized on 2026-10-09. Implementation adds separate compile/runtime class quotas under shared total slots/memory, four bounded active jobs by default, and a native pool supporting 1-16 independently provisioned boxes. Each box retains fresh per-test state, distinct UID/GID/CPU/cgroup and independent eight-MiB scratch. Default installations remain one-box and the application runner remains Docker. No new production project, broker or distributed Worker is introduced. See [ADR 0015](adr/0015-compile-runtime-allocation-and-isolate-boxes.md).

Implemented and verified. Windows and Linux Release builds passed without warnings/errors. The full Docker rerun passed 30 Domain and 208 integration tests (11 skips); final native validation passed 30 Domain and 216 integration tests (4 skips), including two-box independence/cancellation and the real-Worker twenty-job workload. Twenty submissions with 100 tests each finished in 39.848 seconds at two active jobs and compile/run quotas 1/1, versus 28.498 seconds at eight jobs and quotas 2/2; queue P95 fell from 37.489 to 16.734 seconds. Every successfully compiled submission executed every test. The experiment helper/service/cgroup/mounts and fixture resources were removed, and the original application Worker was restarted. The application runner remains Docker. Evidence, initial failed diagnostic runs and measured limitations are recorded under ignored `artifacts/judging-multibox-20261009/` and the [performance report](judging-performance.md). Two-box correctness/performance is measured; larger supported configurations still need their own host validation and benchmark.
